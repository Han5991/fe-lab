# strict-design

규칙은 실행 경로(tsc·lint·테스트·훅)에 있을 때만 규칙이다. 주석·문서·에디터에서만 도는 검사(`$schema`)는
경로가 아니다 — `.ts` + `as const satisfies`나 빌드 시작 검사로 옮긴다. 할 일은 둘: 경로를 설계하고, 정직하게
통과한다.

## 1. 단일 출처

같은 개념의 출처는 하나다. 새로 적기 전에:

1. **찾는다** — 개념·필드 이름과 리터럴 값으로. 기존 출처는 `as const satisfies`·`keyof typeof`로 나온다.
   범위를 좁히지 않는다 — 테스트를 빼는 필터(`grep -v test` 등)를 쓰지 않고, e2e·스크립트·설정·문서도 본다.
   좁혔다면 결론에 범위를 적는다.
2. **있으면 파생한다** — `keyof typeof`, `(typeof X)[number]`, `Pick`·`Omit`, 인덱스 접근, 매핑 타입,
   `Parameters`·`ReturnType`, 생성 타입, 설정의 `extends`.
3. **없으면 값 하나를 세우고** 타입·키 목록·가드를 거기서 뽑는다. 타입을 먼저 적고 값을 맞추면 출처가 둘이다.

   ```ts
   const STATUS_LABEL = {
     draft: '초안',
     published: '공개',
   } as const satisfies Record<string, string>;
   type Status = keyof typeof STATUS_LABEL;
   const isStatus = (v: unknown): v is Status =>
     typeof v === 'string' && Object.hasOwn(STATUS_LABEL, v);
   ```

4. **출처는 개념의 소유자에.** 패키지는 소비처의 값도 분류 체계도 모른다 — 앱이 넘기고, 패키지에 기본값은
   없다.
5. **import할 수 없는 사본만**(런타임·생성 경계) 남긴다. 테스트로 잠그고, 이유를 옆에 적는다.

**분산 신호** — 보이면 멈춘다.

- 같은 필드 묶음·리터럴(경로·이벤트 이름·상태 값)·설정 플래그가 두 곳에 있다.
- 같은 이름이 두 뜻이거나 같은 뜻이 두 이름이다. 같은 이름의 가드가 자리마다 다르게 판정한다. 배럴에서 같은
  이름이 두 경로로 나간다.
- 변형마다 함수가 하나씩 있다(테마별·환경별) — 소비처가 분기를 다시 만든다.
- 키 목록·리터럴에 단언을 붙인다 — 파생을 단언으로 대신했다.
- "A를 바꾸면 B도"·"어긋나면 안 된다" 주석을 쓰고 있다 — 그 주석이 잠기지 않은 사본이다.

## 2. 타입 계약

- 비슷한 옵션 둘 대신 한 옵션을 유니온으로 — 우선순위 규칙이 생기지 않는다.
- 필수면 필수로. `?` + "반드시 지정" + 조용한 기본값은 거짓말이다. 형태는 타입이, 값은 초기화 지점 검사가
  맡는다(호출마다 도는 경로는 던지지 않는다).
- 실제로 흐르는 `undefined`는 `| undefined`로 — 객체 말고 타입을 고친다.
- 바깥 입력(JSON·storage·fetch·설정)은 `unknown`에서 좁힌다(`as Partial<T>`는 확인 전에 계약을 붙인다).
  돌려줄 때는 `unknown` 대신 필요한 구조적 부분형으로.
- null·빈 값은 진입점에서 끊는다. 빈 배열·빈 문자열 폴백은 멈춘 동작을 숨긴다.
- 경계 검증을 넣으면 잘못된 입력의 동작(출력·종료 코드)이 바뀐다 — 동작 변경이다. 동작 보존이 조건이면 기존
  동작을 지키거나 묻고, 바꿨다면 보고와 테스트에 적는다.
- 잊으면 조용히 꺼지는 opt-in 대신 실패가 번지지 않는 구조로. 함께 지워질 값은 한 키에 — 고아 상태를 표현할
  수 없게.
- `as unknown as` 대신 제네릭. 불리언 매개변수 이름은 무엇을 켜는지 말한다.
- 라이브러리 export를 덮어쓰지 않는다 — 명시적 import로 바꾸고 직접 import를 lint로 막는다.

## 3. lint 설계

- 허용만 나열한다(기본 disallow). 금지 목록은 새 파일·폴더가 조용히 통과한다.
- 경계는 이름이 아니라 경로로. element는 폴더 단위다 — 파일 하나를 우회 배정하면 그 폴더의 새 파일이
  뒷문이 된다. 배럴의 `export *`도 경계를 넘으니 export도 검사한다.
- 모두가 import 하는 최하단 레이어가 우회 통로다 — 제일 엄격하게.
- 예외는 설정의 좁은 `files` 블록 + 사유 주석뿐이고, 주석으로 끄는 길은 막는다 — 규칙 변경이 곧 설정 diff다.
- lint가 못 보는 것은 소스 텍스트를 읽는 테스트로 잠근다. 도구 버전을 내리기 전에 원인을 끝까지 추적한다.
- 게이트는 깨지면 **조용히 새는** 것에만 만든다. 재평가 날짜는 AGENTS.md의 게이트 규칙대로.

## 4. 빨간 줄을 만났을 때

목표는 에러를 없애는 게 아니다. 화살표 왼쪽밖에 길이 없어 보이면 **멈추고 이유와 숫자를 들고 묻는다** — 그
변경은 위반 수정과 다른 커밋으로.

- `as X`, `as unknown as X` → 출처 타입을 고치거나 `unknown`에서 좁힌다
- non-null 단언 → 순회·구조 분해로 인덱스를 없앤다. 불변식이 코드에서 바로 읽힐 때만 근거 주석과 함께
- 폴백 값, 새 분기 → 런타임 경로를 바꾸지 않는다. 필요하면 명시적으로, 실패를 삼키지 않게
- 규칙만 통과하는 기계적 치환(점 표기를 대괄호로) → 의미를 본다 — 빌드 도구가 특정 표기만 치환하는 자리가
  있다
- `void`로 floating promise 달래기 → promise를 돌려주지 않는 API로
- inline disable, `files` 예외, `warn` 강등, 문턱·`ignores`, 플래그 끄기 → 하지 않는다 — 묻는다
- 호출부가 많아 별칭·옛 이름을 남긴다 → 전부 바꾼다. 범위가 문제면 호출부 수를 들고 묻는다
- 명시 선언 + 추론 폴백 → 선언 하나로
- 통과하던 테스트를 mock으로 초록으로 → 동작이 바뀐 것이다 — 원인을 찾고 assertion은 그대로
- `--no-verify`, "환경 문제", "내 변경 탓 아님" → 깨진 경로를 찾는다
- 찾은 문제를 "범위 밖"으로 → 보고하고 묻는다

반대 방향도 실패다 — 몇 줄 고치려고 수백 줄, 도달할 수 없는 상태를 손으로 만든 테스트, 아무도 안 쓰는
API·옵션. 추가하는 코드는 그것이 막는 것보다 싸야 한다.

## 5. 증명

- **먼저 센다.** 플래그·규칙을 하나씩 켜고 규칙별·프로덕션/테스트별 위반 수를 센다. 0건부터 켜고 나머지는
  숫자와 함께 보류한다.
- **고치는 순서:** 구조 → 타입을 정직하게 → 명시적 폴백 → 근거 주석을 단 단언.
- **일부러 깨뜨린다.** 막을 방향마다, 셀렉터가 덮을 형태마다 위반을 넣어 발화를 보고 원복한다.
- **0건은 의심한다.** "위반 없음"과 "아무것도 안 봄"(얕은 규칙, 꺼진 타입 인식)을 가르는 양성 대조를 둔다.
  고친 것과 무관하게 통과하는 확인은 확인이 아니다.
- **경계·게이트의 범위를 바꾸면** 그 범위를 서술한 문서·주석을 검색해 함께 고친다.
- **커밋 본문에 남긴다:** 규칙별 before→after, 남긴 단언의 근거, 프로브 결과, 비용.

## 6. 끝내기 전에

아래는 리뷰에서 실제로 돌아온 질문이다.

- 안 만들면 무엇이 깨지나? 깨지면 조용히 새나, 시끄럽게 터지나?
- 이 diff가 새로 만든 사본·예외·인자는? 내 diff에도 §1을 돌렸나?
- 패키지가 소비처의 이름·분류를 알게 됐나?
- 미룬 게 있나? 그 확인은 실패할 수 있었나?
- 남은 단언·예외마다 근거를 한 줄로 말할 수 있나?

## 이 문서를 고칠 때

규칙만 적는다. 경로·심볼·사건 이력·현재 수치는 적지 않는다 — 코드가 바뀌면 문서만 옛 상태에 남는다. 예시는
저장소와 무관한 짧은 코드로.
