# strict-design

이 저장소의 코드는 대부분 에이전트가 쓰고 사람이 감독했다. 아래 규칙과 질문은 감독자가 실제로 되돌려 보낸
자리에서 나왔다. 이 스킬의 목적은 그 질문을 받기 전에 스스로 답하는 것이다.

**전제: 이 문서는 안내이고, 강제는 실행 경로(tsc·lint·테스트·훅)가 한다.** 실행 경로에 없는 규칙은 규칙이
아니다. 그래서 여기서 하는 일은 둘뿐이다 — 그 경로를 설계하는 것, 그 경로를 정직하게 통과하는 것.

## 1. 단일 출처 — 타입은 쓰기 전에 찾는다

같은 개념의 출처는 하나다. 타입·상수·리터럴을 새로 적기 전에 순서대로:

1. **찾는다.** 개념 이름·필드 이름·리터럴 값으로 검색한다. 비슷한 모양이 있으면 그게 출처 후보다. 이
   저장소가 출처를 어떻게 세우는지도 문서가 아니라 코드에서 본다 — `as const satisfies`·`keyof typeof`로
   검색하면 지금의 출처들이 나온다.
2. **있으면 파생한다.** `keyof typeof`, `(typeof X)[number]`, `Pick`·`Omit`, 인덱스 접근, 매핑 타입,
   `Parameters`·`ReturnType`, 생성 타입. 같은 필드를 손으로 다시 적지 않는다.
3. **없으면 값 하나를 출처로 세운다.** 테이블 하나에서 타입·키 목록·가드를 뽑는다. 타입을 먼저 적고 값을
   거기 맞추면 출처가 둘이 된다.

   ```ts
   const STATUS_LABEL = {
     draft: '초안',
     published: '공개',
   } as const satisfies Record<string, string>;
   type Status = keyof typeof STATUS_LABEL;
   const isStatus = (v: unknown): v is Status =>
     typeof v === 'string' && Object.hasOwn(STATUS_LABEL, v);
   ```

4. **출처는 그 개념의 소유자에 둔다.** 패키지는 소비처의 어휘를 모른다 — 값(경로·이름)뿐 아니라 분류
   체계(어떤 갈래가 있고 갈래 이름이 무엇인지)도. 앱이 넘기고, 패키지에는 기본값이 없다.
5. **피할 수 없는 사본은 테스트로 잠근다.** 런타임이 다르거나 생성 파일 경계라 import 할 수 없을 때만이다.
   왜 사본인지를 사본 옆에 적는다.

**분산 신호** — 보이면 멈추고 출처를 찾는다.

- 같은 필드 묶음을 인라인 타입으로 다시 적는다.
- 같은 이름이 두 뜻이거나, 같은 뜻이 두 이름이다.
- 같은 리터럴(경로·이벤트 이름·상태 값)이 두 파일에 있다.
- 변형마다 함수가 하나씩 있다(테마별·환경별) — 둘 다 필요한 소비처가 결국 자기 쪽에서 분기를 다시 만든다.
- 같은 이름의 가드·헬퍼가 여러 벌이고 자리마다 판정이 다르다.
- 배럴에서 같은 이름이 두 경로로 나간다 — 한쪽이 조용히 이긴다.
- 키 목록·리터럴에 단언을 붙인다 — 파생을 단언으로 대신한 것이다.

## 2. 타입 계약

- **인자를 늘리지 말고 유니온으로.** 비슷한 옵션 두 개는 우선순위 규칙을 하나 더 만든다. 한 옵션의 타입을
  유니온으로 둔다.
- **필수면 필수로.** `?` + 문서의 "반드시 지정" + 조용한 기본값은 거짓말이다. 형태는 타입이, 값은 초기화
  지점의 런타임 검사가 맡는다(호출마다 도는 경로는 던지지 않는다).
- **optional은 정직하게.** 실제로 `undefined`가 흐르면 `| undefined`를 붙인다 — 객체를 고치지 말고 타입을
  고친다.
- **바깥 입력은 `unknown`에서 좁힌다.** JSON·storage·fetch 응답·설정 파일. `as Partial<T>`는 확인하기 전에
  계약을 붙인다.
- **`unknown`을 돌려주지 않는다.** 소비자가 에러 갈래를 못 본다. 필요한 만큼의 구조적 부분형으로 좁힌다.
- **null·빈 값은 진입점에서 끊는다.** 빈 배열·빈 문자열 폴백은 화면이 안 깨질 뿐 동작이 멈춘 걸 숨긴다.
- **잊으면 조용히 꺼지는 안전장치를 두지 않는다.** 필드마다 붙이는 opt-in 대신, 실패가 번지지 않는 구조로.
- **고아 상태를 표현할 수 없게.** 함께 지워져야 하는 값은 한 키, 한 객체에 둔다.
- **에디터에서만 도는 검사는 검사가 아니다.** `$schema`보다 `.ts` + `as const satisfies`, 아니면 빌드 시작
  검사.
- **`as unknown as` 대신 제네릭.** 받은 타입을 그대로 통과시키면 단언이 필요 없다.
- **불리언 매개변수 이름은 무엇을 켜고 끄는지 말한다.**
- **라이브러리 export를 덮어쓰지 않는다.** 업스트림이 바뀌면 다시 만들어야 한다 — 명시적 import로 바꾸고
  직접 import를 lint로 막는다.

## 3. lint 설계

- **허용만 나열한다.** 기본은 disallow다. 금지 목록 방식은 새 파일·새 폴더가 조용히 통과한다.
- **경계는 경로로 건다.** 이름 기반 규칙은 별칭으로 우회된다. element는 폴더 단위다 — 파일을 다른 element로
  우회 배정하면 그 폴더에 새로 생긴 파일이 뒷문이 된다.
- **주석으로 끄는 길은 없다.** 예외는 설정 파일의 좁은 `files` 블록 + 사유 주석뿐이다. 그래서 규칙이 바뀌는
  PR은 설정 파일이 바뀌는 PR이고, 리뷰는 그 diff만 보면 된다.
- **가장 아래 레이어가 우회 통로다.** 모든 레이어가 import 할 수 있는 최하단 레이어로 re-export·부수효과·JSX가
  새어 든다. 제일 엄격하게 둔다.
- **배럴의 `export *`도 경계를 넘는다.** 의존 검사에 export를 포함한다.
- **0건은 의심한다.** 규칙이 얕지 않은지(타입 인식 규칙이 꺼져 있지 않은지) 먼저 본다.
- **도구 버전을 내리기 전에 원인을 끝까지 추적한다.**
- **lint가 못 보는 것은 적어 두고, 소스 텍스트를 읽는 테스트로 잠근다.**
- **규칙의 값을 따진다:** 깨지면 조용히 새는가, 시끄럽게 터지는가. 조용히 새는 것만 게이트로 만든다. 모든
  규칙이 게이트일 필요는 없다. 새 게이트의 재평가 날짜는 AGENTS.md의 게이트 규칙을 따른다.

## 4. 빨간 줄을 만났을 때

목표는 에러를 없애는 게 아니다. 아래 표의 왼쪽은 하지 않는다. 왼쪽밖에 길이 없어 보이면 **멈추고 이유와
숫자를 들고 묻는다.** 그 변경은 위반 수정과 같은 커밋에 섞지 않는다.

| 회피                                                                                        | 대신                                                                                           |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `as X`, `as unknown as X`                                                                   | 출처 타입을 고치거나 `unknown`에서 좁힌다                                                      |
| non-null 단언                                                                               | 값 순회·구조 분해로 인덱스를 없앤다. 불변식이 코드에서 바로 읽힐 때만 단언하고 근거를 주석으로 |
| 폴백 값, 새 분기                                                                            | 런타임 경로를 바꾸지 않는다. 폴백이 필요하면 명시적으로, 실패를 삼키지 않게                    |
| 규칙만 통과하는 기계적 치환(점 표기 → 대괄호 등)                                            | 의미를 확인한다 — 빌드 도구가 특정 표기만 치환하는 자리가 있다(환경 변수 인라인 등)            |
| `void`로 floating promise 달래기                                                            | 기다릴 이유를 없앤다 — 반환값을 쓰지 않는 호출이면 promise를 돌려주지 않는 API로               |
| inline disable, 설정 `files` 예외, `warn` 강등, 경고 문턱 상향, `ignores` 추가, 플래그 끄기 | 하지 않는다. 필요하면 묻는다                                                                   |
| 고칠 곳이 많아서 별칭·옛 이름을 남긴다                                                      | 전부 바꾼다. 범위가 진짜 문제면 호출부 수를 들고 묻는다 — 혼자 미루지 않는다                   |
| 명시 선언과 암묵 추론을 같이 둔다(선언이 없으면 추론으로 폴백)                              | 선언 하나로                                                                                    |
| 원래 통과하던 테스트를 mock으로 초록으로                                                    | 동작이 바뀐 것이다. 원인을 찾고 assertion은 건드리지 않는다                                    |
| `--no-verify`, "환경 문제"                                                                  | 깨진 경로를 찾는다. "내 변경 때문은 아니다"는 원인이 아니다                                    |
| 찾은 문제를 "범위 밖"으로 넘긴다                                                            | 보고하고 묻는다                                                                                |
| 0건 결과를 그대로 믿는다                                                                    | 검사가 실제로 대상을 보는지 확인한다                                                           |

반대 방향 실패도 있다. 몇 줄 고치려고 수백 줄을 더하는 것, 도달할 수 없는 상태를 손으로 만든 테스트, 아무도
쓰지 않는 공개 API·옵션. 추가하는 코드는 그것이 막는 것보다 비싸면 안 된다.

## 5. 증명

- **먼저 센다.** 플래그·규칙을 하나씩 켜고 규칙별, 프로덕션·테스트별 위반 수를 센다. 0건인 것부터 켜고
  나머지는 숫자와 함께 보류한다.
- **고치는 순서:** 구조 개선 → 타입을 정직하게 → 명시적 폴백 → 근거 주석을 단 단언. 런타임 경로는 바꾸지
  않는다.
- **일부러 깨뜨려 본다.** 막아야 할 방향마다 위반을 넣어 발화를 확인하고 원복한다. 셀렉터가 덮어야 하는
  형태(문·변수 초기화·`export default`)마다 한다.
- **양성 대조를 둔다.** "위반 없음"과 "검사가 아무것도 안 봄"을 구분하는 검사를 같이 둔다.
- **실패할 수 있는 확인인지 본다.** 고친 것과 무관하게 통과하는 확인은 확인이 아니다.
- **커밋 본문에 남긴다.** 규칙별 before→after, 남긴 단언마다 불변식 근거, 프로브 결과, 비용(lint 시간).

## 6. 끝내기 전에 스스로 묻는다

감독자가 실제로 되돌려 보낸 질문이다.

- 이거 왜 필요한가? 안 만들면 무엇이 깨지나?
- 인자를 하나 더 만들었나 — 유니온이면 안 되나?
- 이 타입·상수의 출처는 어디인가? 사본이 생기면 무엇이 갈리나?
- 패키지가 소비처의 이름이나 분류를 알게 됐나?
- 고칠 곳이 많다는 이유로 미룬 게 있나?
- 어떻게 확인했나? 그 확인은 실패할 수 있었나?
- 이 규칙이 지켜지면 얻는 게 뭔가 — 깨지면 조용히 새나, 시끄럽게 터지나?
- 남은 단언·예외마다 근거를 한 줄로 말할 수 있나?

## 이 문서를 고칠 때

규칙만 적는다. 파일 경로·심볼 이름·사건 이력·현재 수치는 적지 않는다 — 코드가 바뀌면 이 문서만 옛 상태에
남는다. 예시가 필요하면 위처럼 저장소와 무관한 짧은 코드로 쓰거나, 코드에서 찾는 방법을 적는다.
